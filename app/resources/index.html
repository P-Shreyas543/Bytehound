1. Introduction & Getting Started

What is the Bytehound?

Bytehound is a hardware-agnostic telemetry and control dashboard for serial devices. It reads framed UART/USB byte streams or Modbus RTU traffic, decodes the payload using a workbook or CSV configuration that you define, and displays the results in live tables, plots, logs, and command panels — all without writing Python code.

Connecting Your Hardware

To get your hardware (NXP, STM32, ESP32, etc.) talking to the app:

  1. Connect your hardware to your computer using a USB cable or Serial adapter.
  2. Make sure your loaded config matches the bytes your device sends. For a framed protocol that usually means [Header] + [ID] + [Length] + [Data] + [CRC]; for Modbus RTU, set parser_type = modbus_rtu. See Section 5 for protocol details.
  3. Launch Bytehound. A bundled example config loads automatically; use Import Config if you want to load your own Excel workbook or CSV config folder.
  4. Click Connect in the toolbar. A Serial Connection Settings dialog will appear:
    • Select your hardware's COM port (e.g. COM7). Click Refresh if it isn't listed.
    • Set the Baud Rate to match your hardware (e.g., 115200).
    • Set Data bits, Stop bits, and Parity if needed (defaults suit most hardware).
    • Click Connect to open the port.
  5. The status LED turns green and the toolbar button changes to Disconnect with a pink background when connected.
If the device is unplugged while monitoring, Bytehound automatically stops logging, closes the worker, and returns the Connect button to its ready state. If the port stays open but no data arrives for several seconds, the LED turns amber and the status reads Connected (No Data).

Active Polling (Auto-Fetch)

If your hardware only sends data when asked (request/response protocol), connect first, then use the Start Auto-Fetch toolbar button. A dialog lets you choose which configured targets are active. The background worker then sends requests based on your config's polling_schedule sheet.

Pipelining and Timings: The Auto-Fetch dialog also allows you to configure Pipeline poll requests. By default, Bytehound sends one request and waits for its response (sequential). Pipelining allows multiple in-flight requests (controlled by Max in-flight), dramatically increasing throughput on hardware that supports it. You can also tune the TX gap (default 100 ms) which enforces a safe minimum spacing between consecutive outgoing polls.

When Auto-Fetch is active, the button text changes to Stop Auto-Fetch and turns pink. Click it again to stop. If your device streams data on its own, leave Auto-Fetch off.

The application is modular. The central Data Table stays in the middle, while dock panels such as Live Plot, Bitfields, Enums, Raw Console, and Activity Log can be dragged, stacked, resized, or hidden. Panel visibility is controlled under View → Panels, and View → Reset Window Layout restores the default arrangement.

Trigger Configuration (Auto-Pause & Logging)

Click the Trigger... button on the Live Plot toolbar to define an automatic action based on a signal's value crossing a threshold. When the configured condition (e.g., Cell Voltage > 4.2) is met in incoming telemetry:

  • Pause Plot: Automatically freezes the plot (switches to Explore mode) so you don't lose the event off the left edge of the screen.
  • Start Logging: Automatically begins recording a Raw + Decoded telemetry session, capturing the event as it happens without manual intervention.

The trigger disarms automatically after firing once. A pink active state on the Trigger button indicates it is armed.

In Live mode the X-axis is anchored at 0 seconds (session start) and expands to the current elapsed time. Plot samples are kept in a bounded in-memory history (default 6,000 points per signal), so very long sessions may show older time ranges with sparse or no plotted points even though the axis still starts at zero.

Bitfields Panel

If your hardware packs multiple Boolean flags into a single integer signal (like Fault states, Relay statuses, or Switch inputs), the Bitfields panel breaks them out into individual ON/OFF rows. The table columns are Frame, Variable, Bit, and State.

Enums Panel

Sometimes hardware sends state integers (e.g. 0 = OFF, 1 = PRECHARGE, 2 = RUN). The Enums panel shows the latest mapping for each configured enum signal with Frame, Variable, Raw, and Label columns.

Raw Console

The Raw Console shows timestamped hexadecimal bytes flowing into and out of the application in real time. Lines are tagged as RX, TX, or ERR, and decode problems appear as [decode] or [decode warning] messages. Use it to debug communication errors or verify packet structures.

Activity Log

The Activity Log tracks major application events: configurations loaded, connections established or lost, logging start/stop, and any error popups. Useful for post-mortem analysis of a test session.

Frame Errors: If the application receives corrupted telemetry packets (e.g., CRC mismatch, invalid payload length, or bad footer), the exact reason will be displayed here as a [WARN] Frame Error message (e.g. [WARN] Frame Error: CRC mismatch on frame 0x9000...). To prevent the log from being flooded during a noisy connection, identical error messages are throttled to appear at most once per second.

Fault Alarms

Bytehound monitors all incoming decoded signals for the words fault or error (case-insensitive) in their Enum Labels or Bitfield states. If a fault is detected (e.g., a bit named "Overvoltage Fault" flips to ON), Bytehound automatically logs an [ALARM] entry to the Activity Log and the Raw Console. This requires no setup—as long as your Variables configuration includes Enums or Bitfields with those keywords, the application will catch them.

Status Bar (bottom-right counters)

A single-line live readout sits in the bottom-right of the window with six fixed-width counters. They are updated continuously while connected and reset whenever you connect, load a new config, or click Edit → Clear Console / Log. The session clock (⏱) counts from the moment you connect — not from config load — so it always reflects actual device uptime. Reading the counters at a glance tells you whether the link is healthy and how the device is responding.

Frames:   1234  |  Errors:  0  |  Timeouts:  0  |  RX:   12.3 KB  |  TX:    1.2 KB  |  Lat:    9.8 ms
CounterWhat it meansWhat to watch for
Frames Total RX frames received and parsed since the session started — both valid and CRC-failed frames are counted here. Should climb steadily while the device is talking. A flat counter means the device has gone silent.
Errors Wire-level parse failures such as CRC mismatch (including Modbus CRC) or footer mismatch. The frame had the right header/length framing, but the integrity check failed. Should stay at 0 on a healthy link. A slowly climbing number suggests electrical noise, a bad cable, or a baud-rate mismatch. A fast climb almost always means the protocol settings (CRC type, byte order, header) in your config don't match the device.
Timeouts Poll requests that did not get a response within the configured timeout_ms. Primarily relevant when Auto-Fetch is on; Modbus manual sends also wait for a response and can increment this counter. 0 on a request/response device that is keeping up. A few timeouts on first connect are normal (the device may still be booting). A continuously rising count means the device is missing requests — try a longer timeout_ms or a slower interval_ms.
RX Total bytes received over the serial port since the session started, in B / KB / MB. Roughly equal to Frames × frame size. A sudden plateau means the device stopped streaming.
TX Total bytes transmitted by the app over the serial port — includes Auto-Fetch poll requests, TX-Command panel sends, and Parameter Editor writes. 0 if you are only listening. Climbs each time you send a command or while polling is active.
Lat Time between the two most recently received frames, in milliseconds. Lower = faster device. This is wall-clock latency between consecutive RX frames, not request-response latency. For a 10 ms streamer expect ~10 ms here. A spike to hundreds of ms means the device hiccuped; if it stays high the link is choked.
Errors vs decode errors. The Errors counter only tracks wire-level CRC failures. Configuration-level problems — for example a frame ID with no matching variables row, a payload shorter than the configured signal layout, or an unsupported data type — are reported in the Raw Console as [decode] … lines and are not counted here.

The Menu Bar Reference

The main window's menu bar provides direct access to all configuration, control, view, and utility functions of the application. Here is an in-depth breakdown of every menu, action, and setting to help you operate the application effectively, even if you are new to serial testing tools:

1. File Menu

The File menu is where you manage Bytehound's connection mappings (decoders) and exit the application safely.

  • Import Config (Ctrl+O)
    What it does: Opens a file selection dialog to load a new protocol definition. You can select an Excel workbook (.xlsx or .xlsm) or a directory containing individual CSV sheets.
    Why you need it: Bytehound is generic; it doesn't know how your hardware packs its bytes until you tell it. Importing a configuration tells the app what each byte represents, what scales/offsets to apply, and how to format names.
    Example: You are testing a new Modbus-based temperature controller. You load modbus_temp_sensor_map.xlsx. Instantly, the main telemetry table updates to display rows for "Zone 1 Temp", "Heater Power %", and "Alarm Bitfield".
  • Export Template (Ctrl+E)
    What it does: Generates a fresh, blank Excel workbook containing the template structure (10 required sheets with correct headers).
    Why you need it: If you are building a new sensor or controller and want to construct a telemetry profile, this gives you a valid starting point without needing to remember column names.
    Example: You want to monitor a custom DIY microcontroller project. You click Export Template, save it as my_project_def.xlsx, and open it in Excel to start typing in your signal names, offsets, and data types (e.g. float32 at byte 4).
  • Exit (Ctrl+Q)
    What it does: Closes the main application.
    Safety Prompt: If the application is currently recording telemetry logs, exiting will show a caution popup. This warns you that closing the app will immediately stop logging and finalize the logs. This prompt is critical because closing the app abruptly without stopping the log would result in losing all buffered decoded data.

2. Edit Menu

The Edit menu allows you to copy real-time data quickly or clear diagnostic clutter from the display.

  • Copy Value (Ctrl+Shift+C)
    What it does: Copies the text contents of the currently selected cell in the center Data Table directly to the operating system clipboard.
    Example: You notice that the "Battery Voltage" signal wiggles to a peak value of 54.38 V and you want to document it. Highlight that cell in the table, press Ctrl+Shift+C, and paste the value into Slack, Notepad, or your bug tracking tool.
  • Copy Table Snapshot (Ctrl+Shift+T)
    What it does: Captures the complete, real-time status of all decoded signals (columns and rows) in the main table and copies them as tab-separated values (TSV) to the clipboard.
    Example: You are running a bench test and want to quickly record the current status of all 50 cell voltages without starting a full session log. Press Ctrl+Shift+T, open Microsoft Excel or Google Sheets, click on cell A1, and press Paste. The entire table will populate instantly with aligned columns.
  • Clear Console / Log (Ctrl+K)
    What it does: Resets all communication statistics (Frames, Errors, Timeouts, RX, TX, Latency) back to zero, clears all historical lines from the Raw Console and Activity Log text panes, and empties the main table's variables.
    Why you need it: If you have resolved a wiring issue that caused thousands of CRC errors, you want to clear the error count so you can monitor if any *new* errors occur. Pressing Ctrl+K gives you a clean slate.

3. View Menu

The View menu manages visual layout docking, themes, and configuration metadata.

  • Panels (Submenu)
    What it does: Contains checkable options for each of the seven interface docks: *Live Plot*, *Bitfields*, *Enums*, *TX Commands*, *Parameter Editor*, *Raw Console*, and *Activity Log*. Unchecking a panel closes it; checking it opens it.
    Why you need it: Docks can be dragged, floating independently, or closed. If you accidentally close a panel (like the Live Plot), you can restore it here.
    Example: When doing read-only telemetry checks, you don't need to send commands. You uncheck *TX Commands* and *Parameter Editor* to hide them, freeing up screen space for the plot panel.
  • Reset Window Layout (Ctrl+Shift+R)
    What it does: Restores all dock panels to their default positions and splits, and returns the window size to standard defaults.
    Example: You dragged the Live Plot to a second monitor and closed the console, and now your layout is disorganized. Pressing Ctrl+Shift+R snaps all panels back to their neat, default locations.
  • Config Info...
    What it does: Displays a dialog summarizing the active configuration profile, showing the total number of parsed variables, valid frame IDs, CRC settings, and the serialdefaults configuration.
  • Theme (Submenu)
    What it does: Switches the visual appearance of the application.
    • Dark: Best for low-light test benches or server rooms, reducing eye strain.
    • Light: Best for bright outdoor environments, test labs, or creating clean, high-contrast screenshots for technical documentation.
    • System: Automatically aligns the app with your Windows operating system light/dark theme settings.

4. Device Menu

The Device menu controls the physical hardware communication and data recording sessions.

  • Connect / Disconnect (F9)
    What it does: Opens the Serial Settings dialog (allowing you to select COM Port, Baud rate, data/stop bits, parity, and timeout) and connects the serial interface. Toggles the connection on/off.
    Example: Plug in your USB-to-Serial adapter. Press F9, click Refresh, select COM5, set the baud rate to match your hardware (e.g. 115200), and click Connect. The connection LED will turn green.
  • Start / Stop Auto-Fetch (F10)
    What it does: Toggles active register polling on devices that follow a request/response (polled) protocol rather than streaming data continuously.
    Example: Your Modbus sensor requires a "Read Input Registers" command to be sent before it replies with the temperature. Enabling Auto-Fetch starts sending these commands automatically at intervals defined in the polling_schedule sheet.
  • Start / Stop Logging (Ctrl+L)
    What it does: Opens the session recording dialog and begins logging data.
    Modes:
    • Raw only: Records raw incoming and outgoing hexadecimal bytes with timestamps directly to a *_raw.csv file. Safest for deep diagnostics.
    • Decoded only: Buffers decoded variables into memory and formats them as a wide Excel spreadsheet (*_decoded.xlsx) with metadata, written on Stop.
    • Raw + Decoded: Records both files simultaneously (highly recommended).

5. Tools Menu

The Tools menu hosts the post-test visual analysis suite and utility preferences.

  • Analysis Suite (Ctrl+T)
    What it does: Opens a separate, non-modal plotting window for offline log analysis.
    Why you need it: It lets you load saved *_decoded.xlsx files from prior test runs, zoom in, place measurement cursors, apply smoothing filters, and overlay multiple runs to compare hardware behavior.
  • Logging Settings...
    What it does: Opens the configuration dialog for internal rotating diagnostics and disk writing schedules.
    Understanding the Settings:
    • Log level (DEBUG / INFO / WARNING / ERROR): Controls how much diagnostic information the application writes to its internal bytehound.log file. If you set it to INFO, it only records major events (starts, connections). If you set it to DEBUG, it logs every transaction details, worker threads, and layout swaps—excellent for debugging connection drops or serial driver glitches.

Setting it to 0.0 s forces an immediate disk write on every packet. This protects against data loss if the computer suddenly loses power, but it causes continuous disk activity which can degrade performance on older or slower drives.
  • Plot Settings...
    What it does: Opens settings for the Live Plot panel.
    Understanding the Settings:
    • History Max Samples: Sets a limit on how many data points the Live Plot retains in memory per signal (default is 6,000). Setting it to 0 or blank means "unbounded" (no limit). If you are running high-speed tests (e.g. 1 kHz) and want to zoom out and view hours of data, increase this number, but be aware that setting it to unbounded will consume more system RAM over long sessions.

3. Controlling Your Hardware

The app isn't just for reading data — you can actively command your hardware over the same serial connection.

TX Commands

The TX Commands panel provides config-defined commands for sending predefined packets to your hardware. Choose a command from the selector, review the generated Packet Preview, then click Send. This is useful for triggering resets, clearing faults, or toggling modes.

Commands with input fields (defined in tx_command_fields) show an inline numeric form. The app validates ranges, applies scale/offset in reverse, appends the encoded field bytes after any static payload_hex, and builds the full packet automatically. Click Build to refresh the preview without transmitting.

Send requires a connection. Packet preview works from the loaded config even before a serial port is open, but Send will refuse to transmit until you connect.

Parameter Editor

The Parameter Editor panel shows all signals in your config that are marked as writable (read_write = RW or W). For each signal you can:

  • See the Live Value column update in real-time as packets arrive.
  • Type a new value (in engineering units, e.g. 12.5 for 12.5 V) in the Write column's input field. Hover over the input to see the numeric range inferred from min_value, max_value, and the signal type.
  • Press Enter or click the Write button. The app validates the range, reverses the scale/offset, encodes the raw bytes, appends the correct checksum, and transmits the packet immediately as a priority TX.

How the value is encoded

The encoding formula is the exact inverse of how the signal is decoded:

raw = (your_value - offset) / scale
encoded_bytes = raw → data_type (uint8/16/32, int8/16/32, float32/64) → byte_order
ProtocolWhat gets sent
Framed A complete framed packet is built for the signal's frame_id. The encoded bytes are placed at the exact start_byte offset (zero-padded payload). Header, length, CRC, and footer are all added automatically per the Protocol sheet.
Modbus RTU An FC 06 (single-register) request is built when the encoded payload is 2 bytes; FC 16 (multi-register) is used for longer payloads. The raw value is encoded using the signal's scale, offset, and byte order, and CRC16/Modbus is appended automatically.
Writes require an active serial connection. If no signals appear in the editor, all signals in your config are set to read_write = R (read-only). Update your Excel config to mark the appropriate signals as RW or W.
Parameter Editor writes are recorded in the Activity Log with the signal name, engineering value, unit, and full raw hex. TX Command sends are also echoed in the Raw Console as TX lines.

Reading a TX packet (byte-by-byte)

Every TX line you see in the Raw Console — whether it came from a TX Command, the Parameter Editor, or an Auto-Fetch poll request — follows the same wire format defined by your Protocol sheet. Use this guide to decode any TX line.

Framed packet — variable length (no tx_pad_length)

Reference packet from the bundled template (Set_Voltage_Limit at 58.5 V on frame 0x0120):

TX, AA 55 01 20 02 49 02 3C 9E EE
AA 55          ← header (2 bytes, from Protocol.header)
01 20          ← frame_id 0x0120 (big-endian, from frame_id_size + byte_order)
02             ← length = 2 (payload bytes only, from length_meaning=payload_only)
49 02          ← payload, little-endian uint16 = 0x0249 = 585 → 585 × 0.1 = 58.5 V
3C 9E          ← CRC16 over header..payload (crc_type, crc_size, crc_byte_order)
EE             ← footer (1 byte, from Protocol.footer)

Framed packet — fixed length (tx_pad_length set)

Same protocol, but with tx_pad_length = 16 and a write of 123 to a uint16 signal on frame 0x0050:

TX, AA 55 00 50 02 7B 00 00 00 00 00 00 00 00 00 00
AA 55                              ← header (2 bytes)
00 50                              ← frame_id 0x0050
02                                 ← length = 2 (payload only — padding is not counted)
7B 00                              ← payload, little-endian uint16 = 0x007B = 123
00 00 00 00 00 00 00 00 00         ← 9 bytes of zero-padding to reach tx_pad_length=16
If your packet ends in zeros with no CRC or footer visible like the example above, that means your config has crc_type = none and an empty footer. If you expected a CRC and footer, open your Protocol sheet and check those two fields. With a CRC and footer configured, the last bytes of the frame would be the CRC + footer, and the zero-padding would sit between the payload and the CRC. tx_pad_length is the total frame length on the wire, including CRC and footer.

Modbus RTU — single-register write (FC 06)

With parser_type = modbus_rtu and modbus_node_address = 1, writing 123 to register address 0x0050:

TX, 01 06 00 50 00 7B 99 8C
01             ← node address (from Protocol.modbus_node_address)
06             ← function code: 06 = Write Single Register
00 50          ← target register address 0x0050 (big-endian, per Modbus spec)
00 7B          ← value to write, big-endian uint16 = 0x007B = 123
99 8C          ← CRC16/Modbus over preceding bytes, little-endian (per Modbus spec)
Modbus byte order is fixed by the spec: addresses and values are big-endian, the CRC is little-endian. The Protocol sheet's byte_order fields are ignored for Modbus.

4. Logging and Data Analysis

Recording Logs

To save your telemetry session for later review:

  1. Ensure you are connected and receiving data.
  2. Click Device → Start Logging (or use the toolbar). Choose Raw + Decoded, Raw only, or Decoded only, then pick the base filename. The button turns pink while logging is active.
  3. The default folder is ~/Documents/Bytehound/. Depending on the selected mode, the app writes:
    • *_raw.csv — timestamped RX/TX hex frames with timestamp, direction, hex, and delta_t_ms columns. The byte-level capture of the session.
    • *_decoded.xlsx — Excel workbook with two sheets: Metadata (app, version, port, baud, config path, session start, logging mode, etc.) and Data (one wide row per complete poll cycle, with a per-frame block of elapsed_ms + frame_id + signals).
  4. When finished, click Device → Stop Logging. This finalises the decoded workbook.

Interop caveat for the length_meaning and crc_coverage alternates. Bytehound's parser and TX builder agree end-to-end on all 16 combinations (32 build → parse round-trip tests cover them with and without a footer). What that proves is internal consistency: Bytehound can decode what Bytehound builds. It does not prove that Bytehound's interpretation of frame_total / header_to_crc / payload_plus_crc / frame_id_to_payload / payload_only / full_frame matches another vendor's protocol that happens to use the same name.

Concretely:
  • frame_total here counts every byte from the start of the header through the footer inclusive — header + frame_id + length + payload + CRC + footer.
  • header_to_crc counts header + frame_id + length + payload + CRC (footer excluded).
  • payload_plus_crc counts payload + CRC only.
  • full_frame CRC covers header + frame_id + length + payload + footer (every byte except the CRC field itself).
  • frame_id_to_payload CRC covers frame_id + length + payload (header excluded from CRC).
  • payload_only (CRC) covers just the payload bytes.
If you connect Bytehound to a real device that uses one of these names with even slightly different boundaries, the build/parse will silently mismatch the device — every TX frame will fail the device's CRC, every RX frame will fail Bytehound's CRC. Test the first byte sequence on the wire against your device's reference implementation before trusting these alternates in production.
Same caveat for the escape_mode alternates. Bytehound implements SLIP per RFC 1055, HDLC byte-stuffing with the standard 0x7E flag / 0x7D escape / XOR 0x20 mapping, and COBS per Cheshire & Baker (1999). 134 round-trip tests cover every combination of escape_mode × length_meaning × crc_coverage × footer, plus targeted tests for the worst-case payloads (all-special bytes, frames chunked one byte at a time, three frames in one feed). Internal consistency is proven; vendor interop is not. Some HDLC implementations escape additional control bytes (0x11 / 0x13 XON/XOFF), some COBS variants insert a phantom zero, and at least one well-known "SLIP" device drops the leading 0xC0. Always verify the first wire bytes against your device's reference output before deploying.
Wire format (framed):  [ header ] [ frame_id ] [ length ] [ payload ] [ CRC ] [ footer? ]
Wire format (modbus_rtu):  [ node_addr(1) ] [ FC(1) ] [ data bytes ] [ CRC16(2) ] — FC03/FC04 read, FC06/FC16 write
modbus_rtu is fully supported. Set parser_type = modbus_rtu and the parser and TX builder switch to standard Modbus RTU mode automatically. In this mode the id_or_address column in Variables and PollingSchedule is the Modbus register address (not a frame ID).

Fixed-length TX (tx_pad_length) — for buffer-full RX interrupts

Many microcontrollers receive serial data using a buffer-full or DMA-complete interrupt: the ISR fires once N bytes have arrived, and the firmware parses that fixed-size block. If your host sends commands of varying length, those firmwares either miss bytes, split commands across two interrupts, or sit waiting for bytes that never come. Setting tx_pad_length makes Bytehound transmit a constant-size frame for every command, regardless of payload.

Wire layout when padding is active:

[ header ][ frame_id ][ length ][ payload ][ 0x00 0x00 … ][ CRC ][ footer? ]
└──────────────── padded region ────────────────┘
└──────────────── tx_pad_length total bytes ────────────────────────────────┘
  • Padding bytes (0x00) are inserted between the payload and the CRC.
  • The CRC is computed over header + frame_id + length + payload + padding, so the receiver's checksum still matches without any firmware change.
  • The length field still reports the real payload length (not including padding). Firmware that uses buffer-full RX usually ignores this field anyway — it knows the frame size from the buffer size.
  • Only TX is affected. Received frames are still parsed by header + length + CRC as normal.

How to pick the value: set tx_pad_length equal to your MCU's RX buffer size (or DMA transfer count). Example: an STM32 with HAL_UART_Receive_IT(&huart1, buf, 16) needs tx_pad_length = 16.

Worked example. Protocol with header = AA 55, frame_id_size = 2, length_size = 1, crc_size = 2, no footer, and tx_pad_length = 16:

Command with 1-byte payload 0x42 for frame 0x0010 goes out as:
AA 55   10 00   01   42   00 00 00 00 00 00 00   CRC_lo CRC_hi
Total = 2 + 2 + 1 + 1 + 7 + 2 = 16 bytes. The CRC covers the first 14 bytes, padding included.
If a command is bigger than tx_pad_length, the app errors out instead of silently sending an oversized frame — you'll see TX frame (id=0x…) is N bytes but tx_pad_length is M. Either raise tx_pad_length or shrink the command. Also, tx_pad_length must be at least crc_size + len(footer), otherwise there's no room for the CRC and the app rejects the config.
Not for Modbus RTU. Modbus has its own fixed-per-FC framing — tx_pad_length is ignored when parser_type = modbus_rtu.

6. Appearance & Updates

Switching Light / Dark Theme

Open View → Theme and pick one of:

  • Dark — slate background with light text. Best for long monitoring sessions and dim labs.
  • Light — white background with dark text. Best for outdoor / brightly lit environments and screenshots in reports.
  • System — asks Qt to follow the operating system's light/dark preference.

The theme switch is instant. The app reapplies its window styling, rebuilds toolbar/menu icons, retints the live plot canvas, updates the Analysis Suite if it is open, and remembers your choice between launches.

Toolbar and menu icons are theme-aware. In light theme they are drawn with a dark glyph so they remain readable on the white menu background; in dark theme they switch to a light glyph automatically. No restart needed.
System theme caveat. The base Qt palette follows the OS setting, but Bytehound's custom plot, icon, and Windows title-bar tinting are tuned for the explicit Dark and Light choices. If anything looks inconsistent in System, choose Dark or Light directly.

Check for Updates

Open Help → Check for Updates. The app will:

  1. Read the local version.json, contact its configured update manifest over HTTPS, and compare the published version against your installed version.
  2. If you are already on the latest build, show a brief You are on the latest version confirmation.
  3. If a newer version is available, show the version number and release notes and ask whether you want to install it.
  4. On confirmation, download the installer to your system temp folder with a progress dialog. You can cancel while the download is running — the partial file is automatically cleaned up.
  5. Verify the installer SHA-256 checksum against the manifest before launching. If the digest does not match, or if the manifest does not provide a checksum, the install is refused; mismatched or partial downloads are deleted.
  6. After the download is verified, ask one more time before launching the installer in silent mode. The app then exits so the installer can replace the running executable. When the installer finishes, relaunch Bytehound manually.
Update checks are entirely on-demand. The app never contacts the network on its own — nothing is downloaded or installed without your explicit click.
If you see "Failed to check for updates: connection timed out", the manifest server is unreachable from this machine. Check your firewall / proxy settings, or simply skip the update — the app continues to work normally.

Diagnostics & Troubleshooting

If you encounter issues, use Help → Copy Diagnostics. This generates a complete snapshot of your session state—including OS details, Bytehound version, Qt/Python versions, active config path, connection status, packet counters, and the tail of the internal application log. You can paste this directly into a bug report to provide all necessary context in one step without needing to manually hunt down the log file.

7. Application Limitations & Safety Caveats

Bytehound is designed to be highly flexible and performant. However, when using the application for real-time telemetry and control, you must keep the following design limitations and safety constraints in mind:

Performance & Packet Processing Rates

  • Maximum Frame Rate Limit: The Qt GUI telemetry pipeline is optimized and verified to handle packet rates up to 1000 Hz (1 kHz). Above this rate, packet processing and UI redraw operations may consume significant CPU resources.
  • Queue Saturation (⚠️ Queue Saturated): If incoming serial data rates exceed the system's capacity, or if the OS stalls the GUI thread (e.g., during window dragging), the serial packet queue or log flush queue may saturate. When this happens, a yellow warning badge appears in the bottom status bar, and newer packets/logs will be dropped to protect system memory.
  • Odd Byte Widths: Decoded signal widths of 1, 2, 4, and 8 bytes use highly optimized struct unpacking routines. Signals with odd widths (3, 5, 6, and 7 bytes) fallback to slower binary conversions, which can impact performance at high frame rates.

Data Logging & Buffer Safety

  • In-Memory Decoded Log Risk: While the Raw CSV log (*_raw.csv) is continuously flushed to disk at a configurable interval (default 0.5 seconds), the Decoded Excel log (*_decoded.xlsx) is buffered entirely in system memory. It is only written to disk when you click Stop Logging. If the application crashes, the computer loses power, or is killed before you stop logging, the decoded spreadsheet data will be lost. Always stop logging manually before closing the app or disconnecting power.
  • Plot History Limits: Plot history is stored in a fixed-capacity ring buffer (default 6,000 samples per signal). In long monitoring sessions, older points will wrap around and be discarded from memory to prevent memory leaks. Consequently, scrolling back to the beginning of a multi-hour test in the Live Plot is not supported; use the Analysis Suite on the saved log files instead.
  • Raw Console and Log line limits: The Raw Console is capped at 3,000 blocks/lines of history, and the Activity Log is capped at 5,000 blocks. Old messages are automatically truncated from the display buffer.

Dock Window CPU Optimization (Data Gaps)

  • Hidden Dock Optimization: To save CPU cycles on low-spec hardware, the application stops buffering plot history, formatting console strings, and generating bitfield/enum table items for any panel that is currently hidden or collapsed. If you close the Live Plot, Raw Console, Bitfields, or Enums dock, telemetry points for that period are skipped. When you re-open the dock, data resumes plotting from that moment onward, resulting in a gap in the timeline. Keep panels visible if you need continuous live visualization.

Configuration Constraints

  • Silent Overwriting: The configuration importer parses files sequentially. If you define duplicate entries—such as two tx_commands with the same name, or two enums values for the same signal—the latter entry overwrites the former silently without raising a warning. Make sure your names and enum states are unique.
  • Modbus RTU Specifications: The Modbus RTU protocol specifies big-endian encoding for register addresses and data values, and little-endian encoding for the CRC checksum. Custom byte_order configurations in the Protocol sheet are ignored when parser_type = modbus_rtu is selected.
  • Polling vs. Streaming: Do not enable Auto-Fetch (F10) on a device that is already streaming data automatically (unsolicited). Sending poll requests to a streaming device will cause transmission collisions and corrupt the incoming data packets.
