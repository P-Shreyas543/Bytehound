Serial Monitor App: User Manual and Firmware Guide

Welcome to the Serial Monitor App. This documentation serves as a comprehensive handbook for firmware engineers, system integrators, and UI users. It explains the core architecture, the configuration-driven protocol definitions, and the exact data flows required to send frames to the application and visualize data in real time.

1. Configuration Architecture

The entire application is driven by a directory of CSV configuration files. The desktop interface dynamically builds its views, polling sequences, and protocol parsers based on the definitions in these files. You do not need to recompile the application to add new variables or change the protocol.

Configuration File Purpose
protocol.csv Defines the core communication standard. It specifies whether to use modbus_rtu or a custom framed parser. For framed parsers, it dictates the header bytes, length logic, and CRC algorithms.
variables.csv The dictionary of signals. Maps incoming raw bytes to physical values. Defines the data type (e.g., uint16, float32), byte order, scale/offset math, and specific register addresses or payload start bytes.
polling_schedule.csv Instructs the serial worker thread which Target IDs (or Slave Addresses) to poll, and at what millisecond interval.
tx_commands.csv & tx_command_fields.csv Defines static or dynamic transmission packets, such as "Reset" commands or structured parameter updates, enabling the Parameter Editor UI to push data to the hardware.

2. Modbus RTU Implementation

The Serial Monitor natively supports Modbus RTU standards. To enable this, ensure parser_type is set to modbus_rtu in your protocol.csv.

Function Codes and Memory Mapping

  • Read Holding Registers (FC 03): Used automatically when variables are defined with register_type = holding.
  • Read Input Registers (FC 04): Used automatically when variables are defined with register_type = input.
  • Write Single Register (FC 06): Triggered by the Parameter Editor for 16-bit variables marked with read_write = RW.
  • Write Multiple Registers (FC 16): Triggered by the Parameter Editor when writing multi-register data types, such as 32-bit floats or 32-bit integers.

Data Types & Byte Order

Modbus naturally transmits 16-bit registers in Big-Endian format (high byte first). When extracting larger multi-register types like float32, the arrangement of those registers can vary by microcontroller architecture. The byte_order column in variables.csv handles this:

  • big (ABCD): High word first, low word second. Standard for big-endian systems.
  • little (DCBA): Low word first, high word second. Common on little-endian x86/ARM targets.
  • big_word_swap (CDAB) or little_word_swap (BADC): Specialized middle-endian arrangements.
Optimization: The polling engine automatically groups contiguous Modbus register addresses into a single bulk read request to minimize serial overhead. For example, variables at address 40001, 40002, and 40003 will trigger a single FC03 request for length 3.

3. Custom Framed Protocol Implementation

If your embedded device does not use Modbus and instead broadcasts proprietary binary packets, set parser_type = framed in protocol.csv.

Wire Format Structure

The parser expects a generic envelope that must contain the following segments in exact order:

[ Header ] + [ Frame ID ] + [ Length Byte(s) ] + [ Payload ] + [ CRC ]
  • Header: Defined by header (e.g., AA 55). The app scans the serial buffer to synchronize on these magic bytes.
  • Frame ID: Size defined by frame_id_size. This ID corresponds to the id_or_address column in variables.csv to determine how to decode the payload.
  • Length: Size defined by length_size. The length_meaning column defines whether this byte represents the payload_only size, or the total frame size.
  • Payload: The raw binary data. Variables extract data from this array using their start_byte index.
  • CRC: The checksum to validate integrity. Options include crc16_modbus, crc16_ccitt, and crc32. The crc_coverage column dictates which bytes are included in the math (e.g., header_to_payload, id_to_payload, payload_only).

Extracting Variables from Payload

When a valid frame with ID 0x1000 is verified, the app checks variables.csv. If a variable is configured with start_byte = 0, data_type = uint16, and byte_order = little, the engine will extract the first two bytes of the payload, treat them as a little-endian unsigned integer, and then apply scaling math.

Scaling Mathematics

All extracted raw binary values undergo physical scaling before visualization:

Physical_Value = (Raw_Integer_Value * scale) + offset

For example, if the microcontroller transmits a voltage of 12.3V as the integer 123, you would set scale = 0.1 and offset = 0.0.

4. Firmware C Code Examples

Below are concrete examples of how to format and transmit packets from an embedded microcontroller using standard C code.

Example: Sending a Custom Framed Packet

Assuming protocol.csv is configured for framed, Header AA 55, 2-byte Frame ID (Big-Endian), 1-byte Length (Payload Only), and CRC16-Modbus (Coverage: Header to Payload).

#include <stdint.h>
#include <stddef.h>

// Mock UART TX function
extern void uart_transmit(uint8_t* data, size_t len);

// Standard CRC16-Modbus Implementation
uint16_t crc16_modbus(const uint8_t *buffer, size_t length) {
    uint16_t crc = 0xFFFF;
    for (size_t i = 0; i < length; i++) {
        crc ^= buffer[i];
        for (int j = 0; j < 8; j++) {
            if (crc & 1) crc = (crc >> 1) ^ 0xA001;
            else         crc = (crc >> 1);
        }
    }
    return crc;
}

void send_telemetry(uint16_t voltage_raw, uint16_t current_raw) {
    uint8_t buf[64];
    size_t i = 0;

    // 1. Header (AA 55)
    buf[i++] = 0xAA;
    buf[i++] = 0x55;

    // 2. Frame ID (0x1000, Big-Endian)
    buf[i++] = 0x10;
    buf[i++] = 0x00;

    // 3. Payload Length (4 bytes for two uint16 variables)
    buf[i++] = 4;

    // --- PAYLOAD START ---
    // Variable 1: Voltage (uint16, Little-Endian)
    buf[i++] = (uint8_t)( voltage_raw & 0xFF );
    buf[i++] = (uint8_t)( voltage_raw >> 8 );

    // Variable 2: Current (uint16, Little-Endian)
    buf[i++] = (uint8_t)( current_raw & 0xFF );
    buf[i++] = (uint8_t)( current_raw >> 8 );
    // --- PAYLOAD END ---

    // 4. CRC Calculation (Header to Payload)
    uint16_t crc = crc16_modbus(buf, i);

    // 5. Append CRC (Little-Endian Wire Order)
    buf[i++] = (uint8_t)( crc & 0xFF );
    buf[i++] = (uint8_t)( crc >> 8 );

    // 6. Transmit via UART
    uart_transmit(buf, i);
}

5. Testing, Debugging & Fake Serial

The Serial Monitor App includes an internal Fake Serial Engine. This is highly useful for validating your CSV configuration files before any microcontroller code is written.

To use this feature, select the Fake COM port in the application settings. The engine will automatically generate mock data matching your variables, construct valid packets (calculating the correct CRCs automatically), and stream them to the decoder. If the UI populates with data, your configuration matches the expected protocol layout perfectly.

Hardware Validation: Once the Fake engine proves your CSV maps are syntactically sound, you can connect the real hardware. Use the internal Raw Hex Logger to compare the actual bytes received from your MCU against the bytes generated by the Fake engine.
