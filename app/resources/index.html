1. Introduction & Getting Started

What is the Serial Monitor App?

The Serial Monitor App is a powerful, hardware-agnostic telemetry and control dashboard. It reads raw byte streams over a serial connection (UART/USB), parses them using a custom dictionary that you define, and displays the data in live tables and high-speed graphs — all without writing any Python code.

Connecting Your Hardware

To get your hardware (NXP, STM32, Arduino, etc.) talking to the app:

  1. Connect your hardware to your computer using a USB cable or Serial adapter.
  2. Ensure your firmware outputs bytes in the standard packet format: [Header] + [ID] + [Length] + [Data] + [CRC]. (See Section 5 for protocol details).
  3. Open the Serial Monitor App.
  4. Click Connect in the toolbar. A Connection dialog will appear:
    • Select your hardware's COM port (e.g. COM7). Click Refresh if it isn't listed.
    • Set the Baud Rate to match your hardware (e.g., 115200).
    • Set Data bits, Stop bits, and Parity if needed (defaults suit most hardware).
    • Click Connect to open the port.
  5. The status LED in the bottom-left turns green and the toolbar button turns pink when connected.
If the device is unplugged while monitoring, the app automatically stops logging and returns the Connect button to its ready state. No manual action is needed.

Active Polling (Auto-Fetch)

If your hardware only sends data when asked (request/response protocol), use the Start Auto-Fetch toolbar button. A dialog will appear to confirm the polling schedule. The background engine will then continuously send data requests based on your config's polling_schedule sheet.

When auto-fetch is active, the button turns pink. Click it again to stop.

2. Core UI Panels & Features

The application is heavily modular. You can drag, drop, stack, and resize any of the panels to build your perfect workspace. Panel visibility is controlled under View → Panels.

The Main Data Table

Located in the center of the screen, this table displays all your decoded numeric variables (like Voltage, Current, or Temperature) in real-time. Columns include:

ColumnDescription
FrameFrame ID in hex (e.g. 0x0010)
GroupSignal group (from config)
VariableSignal name

Right-click any row to add that signal to the Live Plot or copy its value to clipboard.

Live Plot (Multi-Grid)

The Live Plot panel provides a fully flexible, multi-panel oscilloscope-style view of your telemetry data.

Grid Layout

Use the Layout dropdown in the plot toolbar to select how many subplots to display:

LayoutPanelsBest for
1×11Focus on a single signal group
2×12 (stacked)Compare two independent signal groups
1×22 (side by side)Wide-screen dual view
2×24Full dashboard view
2×48High-density telemetry overview

All panels share the same X-axis (time) — panning or zooming one panel moves all of them simultaneously.

Assigning Signals to Panels

Each panel has its own variable strip above it:

  • Click + Add next to a panel label to pick a signal from your loaded config.
  • Each assigned signal appears as a coloured chip button (e.g. ● VoltageA ✕). Click the chip to remove it.
  • Alternatively, right-click any row in the Data Table → Add to Live Plot → choose the panel number from the sub-menu.

Panel assignments and layout are automatically saved and restored between sessions.

View Modes

ModeIndicatorBehaviour
📊 LiveDefaultX-axis always shows t=0 → current time. The view expands automatically as data accumulates.
🔍 ExploreAfter any pan/zoomView is frozen. New data still plots but the window doesn't move. Hint shows: ⟳ Reset View = Live.

Controls

  • ⟳ Reset View button (or Ctrl+R): Snaps back to Live mode instantly.
  • Scroll wheel: Zoom in/out on time axis → enters Explore mode.
  • Click + drag: Pan the view → enters Explore mode.
The X-axis always starts at 0 seconds (session start). There is no rolling window — you always see the complete session history at a glance.

Bitfields Panel

If your hardware packs multiple Boolean (True/False) flags into a single byte (like Fault states, Relay statuses, or Switch inputs), the Bitfields panel breaks them out into individual, readable ON/OFF indicators.

Enums Panel

Sometimes hardware sends state integers (e.g. 0 = OFF, 1 = PRECHARGE, 2 = RUN). The Enums panel translates these raw numbers into clear, readable text labels so you don't have to memorize state codes.

Raw Console

The Raw Console shows the exact Hexadecimal bytes flowing into and out of the application in real-time. Use this to debug communication errors or verify packet structures. RX frames are shown in one color, TX frames in another.

Activity Log

The Activity Log tracks major application events: configurations loaded, connections established or lost, logging start/stop, and any error popups. Useful for post-mortem analysis of a test session.

3. Controlling Your Hardware

The app isn't just for reading data — you can actively command your hardware over the same serial connection.

TX Commands

The TX Commands panel provides custom push-buttons (defined in your Excel configuration) that instantly send predefined hex payloads to your hardware. This is perfect for triggering Resets, clearing faults, or toggling modes.

Commands with input fields (defined in tx_command_fields) show an inline form where you enter numeric values before sending. The app validates the range, scales your input, and builds the full packet automatically.

Parameter Editor

The Parameter Editor panel shows all signals in your config that are marked as writable (read_write = RW or W). For each signal you can:

  • See the Live Value column update in real-time as packets arrive.
  • Type a new value (in engineering units, e.g. 12.5 for 12.5 V) in the Write column's input field. Hover over the input to see the valid range.
  • Press Enter or click the Write button. The app validates the range, reverses the scale/offset, encodes the raw bytes, appends the correct checksum, and transmits the packet immediately as a priority TX.

How the value is encoded

The encoding formula is the exact inverse of how the signal is decoded:

raw = (your_value - offset) / scale
encoded_bytes = raw → data_type (uint8/16/32, int8/16/32, float32/64) → byte_order
ProtocolWhat gets sent
Framed A complete framed packet is built for the signal's frame_id. The encoded bytes are placed at the exact start_byte offset (zero-padded payload). Header, length, CRC, and footer are all added automatically per the Protocol sheet.
Modbus RTU An FC 06 (single register) or FC 16 (multi-register) write request is built, with the raw value encoded using the signal's scale and offset. CRC16/Modbus is appended automatically.
The Write button is only active when connected. If no signals appear in the editor, all signals in your config are set to read_write = R (read-only). Update your Excel config to mark the appropriate signals as RW or W.
The transmitted packet is logged in the Activity Log with the signal name, engineering value, unit, and the full raw hex of the packet sent — useful for verifying correct encoding.

4. Logging and Data Analysis

Recording Logs

To save your telemetry session for later review:

  1. Ensure you are connected and receiving data.
  2. Click Device → Start Logging (or use the toolbar). The button turns pink while logging is active.
  3. The app records all incoming traffic to two files under ~/Documents/Serial-MonitorApp/Logs/:
    • *_raw.csv — timestamped hex frames (byte-perfect replay source)
    • *_decoded.csv — one row per signal per frame (for Excel/Python analysis)
  4. When finished, click Device → Stop Logging.
If the device disconnects while logging is active, logging stops automatically. The log files are always flushed after every frame so no data is lost on unexpected disconnection.

Replaying a Test

To replay a previously recorded session exactly as it happened:

  1. Click File → Load Raw Log and select your *_raw.csv file.
  2. The app replays the test stream through all panels (table, plot, bitfields, enums) as if live.
  3. No serial port connection is needed during replay.

The Analysis Suite

For deep-diving into external test data (Excel logs from the field):

  1. Go to Tools → Analysis Suite.
  2. Click Load Logs and select your Excel .xlsx test files (typically the *_decoded.csv re-saved as .xlsx).
  3. Overlay multiple parameters, place draggable time-cursors to measure deltas, and use the Scatter → X-Y Plotter to graph parameters against each other.

5. Customizing Your Data (The Excel Config)

The Serial Monitor App uses an Excel workbook to know how to decode your hardware's raw bytes, what to call each signal, how to scale it, and how to send commands back. You do not write any Python code — just fill in the sheets.

Quick start: Click File → Export Template, save the .xlsx file, open it in Excel, fill in the sheets described below, save, then click File → Import Config to load it. Changes take effect immediately.

The workbook contains the following sheets in this order. Each section below matches one sheet tab.

Sheet 1 — Protocol

Defines the wire-level packet structure. Exactly one row must have enabled = TRUE. Do not edit this sheet unless you designed the packet format.

ColumnTypeExampleWhat it does
profile_nametextBMS_v2Free-text label for this protocol profile.
parser_typeenumframedframed = custom byte-framed protocol. modbus_rtu = standard Modbus RTU.
header_hexhex bytesAA 55Fixed start-of-frame marker the parser searches for. Space-separated hex bytes.
frame_id_sizeinteger2How many bytes carry the frame ID after the header.
frame_id_byte_orderenumbigbig or little endian for the frame ID bytes.
length_sizeinteger1How many bytes carry the payload-length field.
length_meaningenumpayload_onlyWhat the length field counts. Currently only payload_only is supported.
crc_typeenumcrc16_modbusChecksum algorithm: crc16_modbus, crc16_ccitt, crc32, or none.
crc_sizeinteger2How many bytes the CRC occupies at the end of the frame.
crc_byte_orderenumlittlebig or little byte order for the CRC field.
footer_hexhex bytes(leave blank)Optional end-of-frame marker. Leave blank if your protocol has no footer.
inter_frame_delay_msinteger10Minimum gap (ms) between TX requests. Default 10 ms.
tx_pad_lengthinteger(leave blank)If set, TX packets are zero-padded to this many bytes before the CRC. Leave blank if unused.
enabledTRUE/FALSETRUEOnly one row may be TRUE. The app uses that row and ignores all others.
Wire format:  [ header ] [ frame_id ] [ length ] [ payload ] [ CRC ] [ footer? ]

Sheet 3 — Variables ⭐ (most important)

Each row defines one numeric signal extracted from an incoming frame. The app reads bytes at the computed offset, applies scale and offset, and shows the result in the Data Table.

ColumnTypeExampleWhat it does
id_or_addresshex0x0010Frame ID (framed) or Modbus register address this signal lives in.
signal_nametextPack VoltageUnique name shown in the Data Table. Must be unique within each frame.
data_typeenumuint16Raw data type in the payload: uint8, int8, uint16, int16, uint32, int32, float32, float64.
countinteger12Repeat count. count=12 on a signal named Cell V auto-creates Cell V 1 … Cell V 12 at consecutive byte offsets — no copy-pasting 12 rows.
byte_orderenumlittlelittle (LSB first, most embedded MCUs) or big (MSB first, network order).
scalenumber0.001Multiply the raw integer by this. E.g. raw = 12500, scale = 0.001 → displayed as 12.5.
offsetnumber-40Added after scaling. Formula: value = raw × scale + offset. E.g. temperature sensor with scale=0.1, offset=−40 converts 850 → 45 °C.
unittextVEngineering unit shown in the Unit column (e.g. V, A, °C, %, rpm).
grouptextCell VoltagesGroup name used by CalcGroups for min/max/avg aggregation. Leave blank if not needed.
read_writeenumRR = read-only (default). W = write-only. RW = readable and writable. Only W/RW signals appear in the Parameter Editor.
min_valuenumber0Minimum valid write value. The Parameter Editor rejects inputs below this. Leave blank for no limit.
max_valuenumber5.0Maximum valid write value. Leave blank for no limit.
descriptiontextTotal pack voltageOptional note — not displayed in the app.
enabledTRUE/FALSETRUESet FALSE to hide this signal from all panels without deleting the row.
Byte offsets are computed automatically. Signals within a frame are packed in the order they appear in the sheet. You do not enter a start byte — the loader calculates it from each signal's data_type size.

Example — 4-byte frame 0x0010 with two signals:

id_or_address | signal_name  | data_type | scale | offset | unit
0x0010        | Pack Voltage | uint16    | 0.01  | 0      | V      ← auto-placed at bytes 0–1
0x0010        | Pack Current | int16     | 0.1   | 0      | A      ← auto-placed at bytes 2–3

Sheet 7 — CalcGroups

Computes aggregate statistics across all signals sharing the same group name. Results appear as extra rows at the bottom of the Data Table.

ColumnTypeExampleWhat it does
group_nametextCell VoltagesMust match the group column in Variables for the signals you want to aggregate.
operationspipe-listmin|max|avg|diffStatistics to compute. Any combination of min, max, avg, sum, diff (max − min). Separate with |.
unittextVUnit shown for the calculated rows.

Example — min/max/avg of 12 cell voltages:

  1. In Variables, set group = Cell Voltages for all 12 cell voltage signals.
  2. In CalcGroups add: group_name = Cell Voltages, operations = min|max|avg|diff.
  3. The Data Table shows four extra rows: Cell Voltages min / max / avg / diff, updated live.

Sheet 11 — PollingSchedule

Only needed if your hardware uses a request / response model — i.e. it only sends data when asked. Each row tells the app to periodically send a request packet and wait for a response.

ColumnTypeExampleWhat it does
id_or_addresshex0x0010Frame ID (or Modbus register address) to request.
interval_msinteger100How often to send the request, in milliseconds.
timeout_msinteger50How long to wait for a response before marking the request as timed out.
enabledTRUE/FALSETRUESet FALSE to pause polling for this frame without deleting the row.
If your hardware streams data automatically without being asked (e.g. sends packets every 50 ms on its own), leave this sheet empty and do not use Auto-Fetch. Polling an already-streaming device sends unnecessary requests and may corrupt the data stream.
